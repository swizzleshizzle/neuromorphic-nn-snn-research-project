NEURO·SCOPE — Stage-2 Dashboard

1 · What is delivered

One dashboard shell with interchangeable treatments along three axes. Everything is driven by the trace header topology — region count, neuron counts, pathways, task — never hardcoded to today's five regions.

2 · Foundations

2.1 Region palette — complementary neon

Each region owns one neon hue, used everywhere that region appears (hero neurons, gauge accents, flow nodes, edge color). Spread around the wheel so five clusters stay separable on near-black, harmonious together. The glow value of a firing neuron is its region hue at full brightness — there is no separate "spike color."

RegionRoleHero hue (on dark)Ink hue (on white)
Sensory Cortexinput#3fd2ff cyan#1fa8d8
Hippocampusmemory#ad8bff violet#8a5cf6

When the header declares more regions than five, extend by stepping hue ~50–70° around the wheel at the same saturation/lightness; never reuse a hue within one brain.

3.2 Focus mode

The hero expands to the full stage; both rails become position:absolute overlays translated off-screen (translateX(±101%), transition .34s cubic-bezier(.4,0,.2,1)) and a 24×64px pull-tab appears at each edge to slide a rail back as a floating overlay. The canvas backing store must re-fit to the new stage size on every mode change.

Build note — canvas sizing. Drive the backing store from the canvas's own displayed size (getBoundingClientRect) × devicePixelRatio, and re-fit on mode change via a short timed callback after the layout settles (the rail transition is 340ms) — not only a ResizeObserver. In the prototype runtime, rect reads inside the rAF loop were stale across the grid→flex restructure; a timer-driven re-fit after the toggle is the reliable path. Always keep backing ≥ displayed size so the field is never upscaled/blurred.

5 · The hero — Neuron Field

The centerpiece. The whole brain is small enough (226 neurons in the reference brain) to render every neuron with its real spikes. The hero fuses Panel 1 (activity) and Panel 2 (flow): you watch a sensory pattern propagate → hippocampal recall → prefrontal planning → router gating → motor output, looping across the inference T-window.

5.1 Shared behavior (both treatments)

  • Two clocks. The bottom scrubber steps through episode frames (one per env step; 100 in this trace). Within the current frame the hero auto-loops that frame's inference window (field[r].spikes[T,N], T = 32) so neurons flash through their spike trains; loop rate × propagationSpeed. Scrubbing a frame pauses playback.
  • Additive bloom. Draw neurons and edges with globalCompositeOperation:'lighter' over a translucent background fill that leaves a motion-blur trail (Observatory ~0.26 alpha, Clinical ~0.42). A faint instrument grid sits under everything.
  • Per-neuron render (flash-only). brightness = base + after-glow(prior spike) + flash(current spike from field); radius bumps and a white core appear on spike; shadowBlur scales the bloom (× glowStrength). No membrane channel in v1 (§8.1).
  • Edges. One per declared pathway, colored by source region, carrying 2–3 travelling pulse dots whose brightness tracks live intensity. Router-gated-closed pathways stay dark/dashed.
  • Labels. Region name (uppercase) + N · rate under each cluster; motor neurons labelled with their action (from header.task.action_labels), gated-closed actions marked ✕, the selected action (task.action) marked ◂.

5.2 Flow Map treatment

Flat, schematic, maximally legible — clusters laid left→right in signal-flow order across the stage width.

5.3 3D Cloud treatment

A volumetric, slowly auto-orbiting neuron cloud that reads as a brain while preserving flow order along one axis. Region centers are spread through 3D space (depth-sorted, depth-fogged), so rotation reveals structure.

// model space, flow axis = X; region centers (x,y,z)
sensory     (-0.82, -0.12, -0.34)   8×8 grid card, faces along X
hippocampus (-0.08,  0.05,  0.10)   ellipsoidal cloud (Fibonacci sphere + jitter)
prefrontal  ( 0.52,  0.30, -0.12)   small tetrahedron
router      ( 0.70, -0.04,  0.30)   diamond
motor       ( 0.96, -0.26, -0.18)   cross: up/down/left/right

orbit: rotateY at ~0.22 rad/s · fixed tilt rotateX -0.20 · perspective camZ 4.2
depth sort far→near · fog alpha 0.38→1.0 by depth
auto-fit scale to stage, centered on the cloud's centroid (orbits in place)

The sensory grid card carries the same agent receptive-field highlight (here a pulsing ring) to keep the Panel-3 tie. Auto-fit means the cloud is compact in the narrow Dashboard column and immersive in Focus.

5.4 Engine guidance (production)

The current build renders on Canvas 2D — correct and performant at the 226-neuron "dots" tier. Honor the architecture spec's representation ladder so future, larger brains don't force a rewrite:

N (per header)renderEngine
≤ ~2KdotsPer-neuron, glow+flash. Canvas 2D is fine; WebGL point sprites (pixi/regl/three) recommended day-one to avoid the scaling wall and to make the 3D cloud trivially GPU-rotatable.
~2K–100KcloudWebGL point cloud; pan/zoom to inspect.
> ~100KdensitySink emits an aggregated population field; drill-down to a sampled subset.

Panels use D3 for bespoke visuals (flow network, gridworld, router gates) and Recharts for standard time-series (membrane, rate curves), per the architecture spec.

6 · Panels

All panels read the header for structure and frames for state; none hardcode region names. Each is a var(--panel) card with the standard header.

6.1 Panel 01 — Region Activity

Reads regions[r].rate / active_frac / rate_t. One row per region: accent dot, label, live rate, a normalized bar, a rate_t sparkline with a moving playhead, and a meta line (role · active frac · total spikes · status dot). Purpose: spot dead/runaway regions at a glance.

6.2 Panel 02 — Communication Flow

Reads pathways[p].intensity / gate_open + header pathways (the PFC→Motor id is pfc_motor). A compact node schematic (echoing the hero topology) whose edge stroke width/opacity track live intensity, plus a pathway list tagged OPEN / CLOSED (gate fraction > 0.5) / STORE (the quiescent sens_hippo store edge) with the live value. The schematic, not the hero, is where edge identity is read precisely.

6.3 Panel 03 — Task State

Reads task + header task. The grid_n × grid_n gridworld (reference 5×5): agent (filled, sensory hue), goal (ring, motor hue), last action (arrow), and a readout of agent/goal coords, action, reward, return (sign-colored). Header note → sensory reinforces the receptive-field link to the hero.

6.4 Panel 04 — Thalamic Router

Reads router.gate_open(_t) (per-action fractions) + router.utilities. Actions come from header.task.action_labels (["up","right","down","left"] in this trace). One row per action: utility bar (pre-gate) beside a gate pill showing state + fraction (> 0.5 → OPEN) — the core insight is utility vs. what actually passes. The selected action (task.action) is highlighted.

6.5 Panel 05 — Spike Raster

v1 is flash-only, so this panel renders spike trains from field[r].spikes[T,N] — not membrane V(t). A row per neuron of the selected small planning region (e.g. prefrontal n0–3), ticks where the neuron spiked across the T-window, and a playhead synced to the hero's window loop. When the detail.membrane tier lands later, this slot upgrades to stacked V(t) traces.

8 · Data-driven architecture

The dashboard renders whatever a trace declares. The header's regions[] (id, label, n_neurons, role, render) and pathways[] generate clusters, gauges, flow nodes, edges, and labels; frames supply state. Adding regions or growing neuron counts requires no UI change — only a header that declares them and the §5.4 ladder picking the representation.

Loader (done). The build loads week11_dashboard_trace.jsonl — line 0 = header, each following line = one Frame — into frames[], then renders frames[envStep]. The loader is decoupled from the render path, so a WebSocket source can push the same Frame objects with no render change.

8.1 Data-contract reconciliations (confirmed against week11 trace)

Four points where the real contract differs from the early synthetic prototype. The build honors all four; restate them for any future brain/trace.

#RuleDetail
1PFC→Motor id is pfc_motorNot pfc_router. Drive every edge from header.pathways[].id — never hardcode names.
2gate_open is a fractionIn [0,1], not boolean. OPEN/CLOSED pill threshold > 0.5. router.gate_open and pfc_motor.gate_open are per-action arrays (one fraction per action).
3v1 is flash-onlyNo detail.membrane. Hero glow = spike flashes from field; Panel 05 = spike raster from field, not V(t). Membrane tier deferred.
4Sensory-grid uses encoding.sensory_inputThe agent/goal planes (spikes [T, 2·grid_n²], planes:["agent","goal"], index = y·grid_n + x) — not field["sensory"] (the 64-d latent). The hero's SENSORY INPUT overlay and Panel 03 both read it.
This trace (week11). An untrained brain — 100 steps, never reaches goal (return → −100, ends truncated). The thalamic router fires near-constantly (rate ≈ 0.99 → flagged runaway), and sens_hippo reports gate_open 0 every frame by design (the memory store happens once before the episode, not per-step) — rendered as a quiescent STORE edge, not a bug. A good canonical "debug an early/broken brain" fixture.

10 · Open decisions & recommendations

10.1 Primary hero

Recommendation: ship both. Default the Flow Map in Dashboard mode (propagation legibility for debugging) and the 3D Cloud in Focus mode and for the capstone video (the "honest view and cool view are the same view" payoff). The toggle stays available in both. Confirm before build.

10.2 Interaction depth on the cloud

Next-step candidates, not yet built: drag-to-rotate (pause auto-orbit on grab) and click-a-neuron-to-inspect (pin it into Panel 05). Recommended for the WebGL build where picking is cheap.

10.3 Engine

Build the hero on WebGL from day one (§5.4) even at 226 neurons — it removes the scaling wall and makes the 3D cloud's rotation/picking native.

10.4 Sensory-as-grid mapping — resolved

The contract answers this: encoding.sensory_input ships the true agent/goal planes over the window, so the build renders an exact grid_n×grid_n SENSORY INPUT grid from it (§8.1 rule 4) rather than approximating from the 64-d latent. The 8×8 latent cluster and the 5×5 input grid are deliberately distinct surfaces.

11 · Build-order alignment

This spec slots into the architecture spec's build order: the shell, panels, and both hero treatments are specified here for steps 2–4 (dashboard shell → boring panels → hero). Recommended sequence: shell + tokens → panels 01/03/04 → panel 02/05 → Flow-Map hero → 3D-Cloud hero → wire WebSocket frames. De-risk the data wiring on the panels before the hero, exactly as the architecture spec advises.
